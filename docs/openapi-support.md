# OpenAPI support

Scope: importing a team's OpenAPI spec from Git, generating one page per
operation under `/docs`, an interactive "Try it" playground, and serving
`/openapi.json` on the public site.
Tracking issue: [#26](https://github.com/codelitdev/frontlit/issues/26).
Related: [#65](https://github.com/codelitdev/frontlit/issues/65) (pages from
Git, site releases), [#81](https://github.com/codelitdev/frontlit/issues/81)
(Fumadocs import leaves the OpenAPI mount folder to this issue),
[#82](https://github.com/codelitdev/frontlit/issues/82) (redirect domains),
[#141](https://github.com/codelitdev/frontlit/issues/141) (docs site
performance).

Status: implemented (v1). Target customers are small and medium teams; scope, limits
and operational choices are sized for them and for an early-stage product.

## 1. Context

MediaLit, SendLit and FrontLit's own docs use `fumadocs-openapi` today:
`openapiSource(openapi, { baseDir })` generates one page per operation into a
folder that only holds a `meta.json` (title, icon), rendered with `<APIPage>`
and its playground.

| | Spec | Mount | Auth schemes |
| --- | --- | --- | --- |
| MediaLit | committed `apps/api/src/swagger_output.json` (OpenAPI 3.0.3, 32 KB, 11 operations with `operationId`s, one untagged, `multipart/form-data` upload) | `api/` | per operation: apiKey (`x-medialit-apikey`), bearer, or signature (`x-medialit-signature` header apiKey); some public (`security: []`); server `{protocol}://{host}`, default `https://api.medialit.cloud` |
| SendLit | generated from ts-rest contract, served at `https://api.sendlit.app/openapi.json`, not committed (OpenAPI 3.0.2, 215 KB, 137 operations in 10 tags, no `operationId`s, schemas inlined, JSON bodies only) | `api-reference/` | apiKey or bearer (global); server `{protocol}://{host}`, default `https://api.sendlit.app` |
| FrontLit | generated at build time (`apps/docs/lib/openapi.ts`); served at `/openapi.json` by `apps/api/src/app.ts` | `api-reference/` | — |

All three are single-file OpenAPI 3.0 specs (MediaLit and SendLit checked on
2026-10-25; FrontLit uses the same ts-rest generator as SendLit).

What exists in FrontLit today:

- Nothing in `apps/sites` handles OpenAPI. `openapi.json` is already in
  `RESERVED_PAGE_SLUGS` (`packages/api-contract/src/schemas/pages.ts`), but no
  route serves it.
- `processGitSync` (`apps/api/src/documentation/github/worker.ts`) reads the
  Git tree once per commit, imports pages, then docs. It returns early when
  docs sync is off, when the commit is already live, or when the docs folder
  is unchanged, and a pages error fails the whole job.
- Docs pages are TipTap JSON revisions plus publication memberships. Many
  features read and write them: the editor (`authoring.ts`), Git proposals
  and adoption PRs (`github/proposals.ts`, `github/migrations.ts`), AI
  suggestions (`improvements.ts`) and the admin MCP tools.
- The docs importer turns every `_sections.json` entry into a docs Section,
  including empty ones.
- Page-builder has no Tabs, Table or Collapsible primitive, and its `Select`,
  `Dialog` and `Drawer` primitives are Radix-based.

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| 1 | **The spec path and the URL path are settings in the GitHub integration dialog**, e.g. `apps/api/src/swagger_output.json` published at `/docs/api-reference`. The URL path is reserved for the API reference. | Teams point at the spec where it already lives, with no copy step in CI. Reserving the URL path makes route clashes with Markdown pages impossible by construction. |
| 2 | **The API reference is its own content type with its own live pointer**, independent of the docs publication. | Docs write paths (editor, proposals, adoption PRs, AI suggestions, MCP) never see operations. A broken spec, often generated by CI, doesn't block docs fixes, and a broken Markdown page doesn't block a spec update. |
| 3 | **Each operation is stored as a self-contained slice**: the operation, the components it references, its security schemes and the servers. `$ref`s inside the slice stay as references. | Specs often reference themselves in cycles, so fully dereferenced specs can't be stored as JSON. Slices keep each page small; rendering only needs a cycle guard. |
| 4 | **Specs and slices are stored as JSON `text`, not `jsonb`.** | `jsonb` reorders object keys, which would show schema properties and paths in the wrong order. |
| 5 | **No new package.** Import code lives in `apps/api/src/documentation/openapi/`, the playground's request builder in `apps/sites/components/api-reference/`, and the shared types (slice, playground model) in `packages/api-contract`. | `api-contract` is already shared by both apps; a new package adds build and release setup for no gain. |
| 6 | **We build our own reference and playground from page-builder primitives. No third-party OpenAPI UI or renderer packages** (see "Third-party OpenAPI UIs" below). | The `AGENTS.md` primitives rule, the performance budget in §8, and control over a core part of the product. |
| 7 | **The playground calls the customer API directly from the browser. No proxy in v1.** | A proxy is an SSRF surface and an operational burden. MediaLit, SendLit and FrontLit can allow the docs origin through CORS. |
| 8 | **Operation pages ship no OpenAPI code to the browser.** Everything is computed at import, the reference is server-rendered HTML, and the playground's small script loads only on intent. | The pages are on the public site and must be as fast as a docs article (§8). |

OpenAPI support is Git-only, like the issue proposes. It works with any
GitHub connection, including one that syncs pages only; the docs themselves
can be Git-owned or editor-owned. Teams without a GitHub connection don't
get it in v1; the
admin explains that connecting GitHub enables it.

### Trade-off of decision 2

Docs and the API reference go live independently. After a sync where only
one succeeds, docs can be at commit X and the API reference at commit W. Both
are valid on their own, and the admin shows each one's commit. This differs
from pages-from-Git (#65), where any error fails the whole sync; the spec is
usually a generated artifact, so isolating its failures is worth more than
commit-level atomicity.

### Third-party OpenAPI UIs

These were considered and rejected (2026-10-25):

| Package | Why not |
| --- | --- |
| fumadocs-openapi v12 (headless renderer, playground hooks, code-sample generators) | Its page renderer is a client component, so the whole page hydrates and its data ships to the browser. It requires `fumadocs-ui` and `fumadocs-core`, and its API changed in breaking ways between v10 and v12 within a year. |
| Scalar (`@scalar/api-reference-react`, `@scalar/api-client-react`) | Its own styling breaks the primitives rule. It is a client-rendered single app, not one server-rendered page per operation. |
| Swagger UI, Redoc, Stoplight Elements, RapiDoc | All render the whole spec in the browser with their own styling. Redoc's "Try it" is reportedly paid; Stoplight Elements is reportedly in maintenance mode. |

The reference, schema tree, code-sample generation, request building and
playground are built in-house. Only low-level, non-UI libraries are used for
the import (§6.1).

## 3. Data model

```
documentation_git_bindings
  apiSpecPath, apiMount                                 (dialog settings, §4)

documentation_settings
  activePublicationId ──▶ documentation_publications   (Markdown docs, unchanged)
  activeApiSpecId     ──▶ documentation_api_specs
                            id, teamId, commitSha, sourcePath, sourceBlobSha,
                            mount, spec text, info jsonb, status,
                            diagnostics jsonb, createdAt
                          documentation_api_operations
                            specId, route, title, group, order, method, path,
                            deprecated, slice text, chunks jsonb
                            unique (specId, route)
```

- `documentation_api_specs` holds the live spec and the latest failed
  attempt; nothing else is kept. `status` is `active | failed`. `spec` is the
  served `/openapi.json` (§4). `info` holds the small summary the landing
  page needs (title, version, description, server list, security scheme
  names). `sourceBlobSha` is the spec file's Git blob SHA, used to skip
  unchanged specs.
- `documentation_api_operations` holds the generated pages of the live spec.
  `route` is relative to `/docs` (e.g. `api-reference/upload-a-file`), like
  docs memberships, so the existing search and sitemap URL building works
  unchanged.
- Clearing the spec path in the dialog unpublishes the API reference and
  deletes its rows. A spec file that is missing at a commit is a diagnostic
  (`OPENAPI_NOT_FOUND`) and keeps the last live spec, since a moved or
  deleted file is usually a mistake. Disconnecting or pausing GitHub keeps
  the last live spec, like docs.

## 4. Source contract

One spec per team in v1, configured in the GitHub integration dialog. Both
fields are optional; the API reference is off while the spec path is empty.

| Field | Example | Rules |
|---|---|---|
| OpenAPI spec | `apps/api/src/swagger_output.json` | A repo-relative path to a `.json`, `.yaml` or `.yml` file on the connected branch, inside or outside the site folder. Preflight checks that it exists and is valid. |
| URL path | `api-reference` → `/docs/api-reference/...` | Defaults to `api-reference`. One lowercase slug segment. Not `collections` or `search`, and not a first-level docs folder that holds Markdown. |

- Both are stored on the binding (`apiSpecPath`, `apiMount`) and added to
  `documentationGitSelectionSchema`. Changing either queues a sync. The
  GitHub App is installed per repository, so reading a path outside the site
  folder needs no new permission.
- The URL path is reserved for the API reference: docs route validation
  rejects any Markdown page or frontmatter `slug` that resolves under
  `/docs/<mount>/`.
- The Section is labelled "API Reference" in the sidebar, breadcrumb and
  docs home, and the landing page heading says "API Reference" too. The
  spec's `info.title` and version (e.g. "Medialit API v0.3.0") appear under
  that heading. The API Section comes after the docs Sections.
  `_sections.json` is not involved.
- OpenAPI 3.0 and 3.1, JSON or YAML, in a single file. OpenAPI 2.0 and
  `$ref`s to other files are diagnostics that ask for a 3.x single-file spec.
- **Everything in the spec becomes public**, including when the repo is
  private: the operation pages and `/openapi.json`. Preflight and the admin
  say so. Otherwise the served spec is the committed one, with YAML converted
  to JSON.
- **Hiding operations.** OpenAPI has no standard field for this; `x-`
  fields are tool-specific extensions. FrontLit honours `x-internal: true` on
  operations, the most widely supported convention (Redocly, Stoplight
  Elements, Zuplo, GitBook), and accepts Mintlify's `x-excluded: true` as an
  alias. A hidden operation gets no page, isn't searchable, and is removed
  from the served `/openapi.json`. Hiding only affects the docs; the endpoint
  can still be called, so it is not access control.
- MediaLit points the dialog at its committed `swagger_output.json`. Teams
  that generate the spec only at build time (SendLit, FrontLit) add a CI step
  that commits it, anywhere in the repo.

### 4.1 Limits

Each is a diagnostic when exceeded.

| Limit | Value |
| --- | --- |
| Spec file | 5 MiB |
| Operations | 500 |
| YAML aliases | none (`maxAliasCount: 0`, as in `text-editor/src/docs/frontmatter.ts`) |

## 5. Routes and page identity

- `/docs/<mount>` is the API landing page.
- `/docs/<mount>/<operation-slug>` is an operation page.
  - The slug comes from the first usable of: `operationId`, `summary`, method
    + path. A value that slugifies to nothing (e.g. non-ASCII) falls through
    to the next. Specs generated from ts-rest contracts, such as SendLit's,
    have no `operationId`s, so `summary` gives readable URLs like
    `/docs/api-reference/remove-a-tag-from-a-contact` instead of
    `delete-contacts-contactid-tags-tag`. Changing the value a slug came
    from changes the URL.
  - The page title is `summary`, else method + path.
- Tags only group operations in the sidebar and on the landing page; they are
  not part of the URL. An operation with several tags is grouped under the
  first; untagged operations go under "Other".
- Duplicate `operationId`s (invalid OpenAPI) and duplicate routes are
  blocking diagnostics with both JSON pointers.
- Deprecated operations keep their page and show a "Deprecated" badge.
- Stable anchors on every operation page: `#authentication`, `#parameters`,
  `#request-body`, `#responses`, `#response-<status>`. Search chunks and
  chatbot citations point at these.
- The slug scheme is FrontLit's own; it does not have to match
  fumadocs-openapi or any other tool. Teams moving from another tool map old
  URLs with per-path redirects (#82).
- Portability is a nice-to-have, not a requirement: a plain `openapi.json` or
  `openapi.yaml` with no FrontLit-specific extensions required should also
  work in other docs tools with little or no change.

## 6. Changes by area

### 6.1 Import (`apps/api/src/documentation/openapi/`)

- Load JSON or YAML with the `yaml` package already in the repo, keeping
  source positions for diagnostics and enforcing §4.1.
- Validate with our own checks rather than a full JSON Schema validator: the
  `openapi` version (3.0 or 3.1), `info.title`, `paths`, every internal
  `$ref` resolves, no `$ref`s to other files, unique `operationId`s and
  routes. 3.0 and 3.1 are read directly; nothing is upgraded. These checks
  give precise, readable errors; full validation would reject many real,
  slightly off-spec generated specs.
- Build per-operation slices, routes, anchors and search chunks:
  - one chunk per section of an operation: overview, parameters, request
    body, and one per response status, each with its anchor;
  - every chunk starts with the method, path, title and tag, e.g.
    `POST /media/upload — Upload a file (Media)`;
  - schemas are written as short lines such as
    `name (string, required): description`, not raw JSON;
  - the overview chunk includes the auth requirements.
- Precompute everything a page needs and store it in the slice: example
  bodies (our own small generator: the spec's example, default, const or
  first enum value, else a value built from the types), code samples (curl, JavaScript, Python, plus
  `x-codeSamples`), parsed descriptions and the playground model (§8.3).
  Code samples use the first server and placeholder credentials; they don't
  follow the server picked in "Try it".
- Auth requirements follow OpenAPI's rules: an operation's own `security`
  overrides the global one; `security: []` marks a public endpoint; several
  requirement objects mean "any one of these"; the schemes inside one object
  are all required together.
- Descriptions: try `parseDocsMarkdown`; fall back to escaped plain text with
  a **warning**, because that parser rejects HTML and many real specs
  contain HTML in descriptions.
- URLs taken from the spec (`info.contact`, `license`, `termsOfService`,
  `externalDocs`, server URLs) are kept only if they are `https:`, `http:` or
  `mailto:`; others are dropped with a warning.
- Fixtures: the real MediaLit, SendLit and FrontLit specs.

### 6.2 API (`apps/api`)

**Sync.** A new step at the **start** of `processGitSync`, before pages and
docs, so none of their early returns or failures can skip it:

1. Skip when `apiSpecPath` is empty, or when the spec file's blob SHA and
   the two settings match the live spec.
2. Read the file with the existing `readBlob`, run the import (§6.1), and
   store the result: a `failed` row with diagnostics, or a new spec ready to
   activate.
3. Activate in one short transaction: re-check that the connection
   generation, spec path and URL path are unchanged (otherwise a newer sync
   imports again), replace the operation rows, delete the previous spec row, set
   `activeApiSpecId`, and insert an outbox event that invalidates
   `docs:<team>` and `sitemap:<team>` on the sites and, when configured, the
   edge cache (the same destinations as a docs activation). The event is a
   new type, `api_reference`, which the sites webhook accepts. The worker is
   woken right away so the change is live within a second.
4. The step catches its own errors and records them on its row. It never
   fails the sync job; pages and docs run as before.

**Docs integration.** Docs route validation (`importDocumentationTree` and
editor validation) rejects routes under `/docs/<mount>/` (§4). Links from
docs pages to operation pages are not validated in v1.

**Search, chat and sitemap.** These read paths include the live operations:
- lexical search (`searchPublishedDocumentation`) scores operation chunks
  alongside doc chunks. Semantic embeddings for operations are deferred
  (§10), so operations are always matched lexically, also for teams in
  semantic mode;
- `SearchResult` (`documentation/queries.ts`) gets `kind: "api-operation"`,
  with the operation's route as its `documentId` and `slug`, so the public
  docs search links to `/docs/<route>#<anchor>` unchanged;
- the chatbot, help-desk copilot and MCP `search_docs` use the same search
  and cite operation anchors. The help-desk copilot records AI evidence
  (`inbox-ai/generate.ts` → `improvements.ts`) only for `kind: "doc"`, so AI
  suggestions never propose edits to generated operation pages;
- `getSitemap` adds operation routes.

**Diagnostics** reuse `DocsDiagnostic`: `file` = spec path, `fieldPath` = JSON
pointer, `line`/`column` from source positions. Codes: `OPENAPI_NOT_FOUND`,
`OPENAPI_PARSE`, `OPENAPI_INVALID`, `OPENAPI_UNSUPPORTED` (2.0, external
`$ref`), `OPENAPI_LIMIT`, `OPENAPI_DUPLICATE_OPERATION`, `ROUTE_COLLISION`.
They appear in preflight (`github/source.ts`), which also reports "N
operations will be published under `/docs/<mount>`; `/openapi.json` will be
public", and in the admin panel (§6.6).

**Public endpoints** (`packages/api-contract`, `apps/api/src/public/routes.ts`):

| Endpoint | Returns |
| --- | --- |
| `GET /public/:teamId/content/api-reference` | Navigation and landing data: mount, `info`, and per operation `route`, `title`, `group`, `method`, `deprecated`. 404 if none. |
| `GET /public/:teamId/content/api-reference/operation?route=...` | One operation: slice, code samples, playground model. |
| `GET /public/:teamId/content/api-reference/openapi.json` | The served spec text, with `ETag` = content hash. |

### 6.3 Public site (`apps/sites`)

- `app/sites/[teamId]/openapi.json/route.ts` proxies the spec endpoint with
  `Access-Control-Allow-Origin: *` so tools can fetch it. This is unrelated to
  the API host's own `/openapi.json` in `apps/api/src/app.ts`.
- `docs/[...slug]/page.tsx`: paths under the API mount render from the API
  reference; other paths keep reading docs.
  - `/docs/<mount>`: the landing page, showing `info` (title, version,
    rendered description, servers, auth overview, link to `/openapi.json`)
    and the operations grouped by tag.
  - `/docs/<mount>/<operation-slug>`: `<ThemedApiOperation>` (server
    component) inside the existing docs layout: method badge and path,
    authentication, parameter tables, request-body schema tree
    (`oneOf`/`anyOf`/`allOf`), responses per status with schemas and
    examples, code-sample tabs, and the "Try it" button.
- Layout: on wide themes the operation page has three columns (docs sidebar,
  content, a sticky code panel with "Try it", code samples and response
  examples). Columns follow the width of the theme's container, not the
  viewport: when it is narrower than 1,024px (Editorial), the code panels
  move below the content and "Try it" sits under the description.
- Reads are cached like docs (`"use cache"` tagged `docs:<team>`) and
  invalidated by the API reference activation event (§6.2).
- `lib/docs-tree.ts` / `DocsSidebar` and the docs home page: the API Section
  is merged in from the `api` endpoint, after the docs Sections, with
  operations under tag labels ordered by the spec's `tags`, then spec order.
  Its Section link goes to `/docs/<mount>`.
- The sidebar is rendered once per page; narrow layouts show it behind a
  CSS-only "Browse articles" toggle. Only the current tag group's operations
  ship with the page. The other groups load from the public `api-reference`
  endpoint on first use (pointer, focus or a click in the sidebar) and, without
  JavaScript, link to their section on the landing page. A 213-operation spec
  keeps operation pages around 240 KB instead of ~950 KB.

### 6.4 Page-builder primitives

Add under `packages/page-builder/src/primitives`:

- `Tabs`: a small hand-written client component (no Radix) with ARIA tab
  roles and arrow-key navigation. All panels are server-rendered, so their
  content is in the HTML before hydration.
- `Table`: stacks rows on narrow screens.
- `Collapsible`: native `<details>`, following the FAQ block's pattern; no
  JavaScript.
- `NativeSelect`: a themed native `<select>`. The playground uses it instead
  of the Radix `Select` to stay within its size budget (§8.3).
- Method and response-status badges built on `Badge`'s existing variants,
  not new colours (see "Theme" below). They always show the method or status
  text, so meaning never depends on colour alone.

Code samples use `Tabs` around the existing `CodeSnippet`. Syntax
highlighting is out of scope; docs code blocks don't have it either.

#### Theme

Every part of the API reference and the playground follows the team's active
theme (`ThemeStyle`), in light and dark mode, like the rest of the site:

- Colours come only from theme tokens (`primary`, `secondary`, `muted`,
  `accent`, `destructive`, `border`, `card`, `chart1`–`chart5`, with their
  foregrounds). There are no hard-coded colours. The theme has no success or
  warning tokens, so the usual green/blue/amber/red method colours are not
  available. The suggested mapping uses `Badge` variants:

  | Badge | Variant |
  | --- | --- |
  | `GET` | `secondary` |
  | `POST`, `2xx` | `default` (primary) |
  | `PUT`, `PATCH`, `3xx`, `4xx` | `outline` |
  | `DELETE`, `5xx` | `destructive` |

- Typography comes from the theme's slots through the primitives: headings,
  body text and captions, and `typography.code` for paths, schemas and code
  samples.
- Surfaces use the theme's interactives: code panels and boxes through
  `interactives.card`, the playground panel through `interactives.dialog`,
  inputs through `interactives.input`, buttons through
  `interactives.button`. Borders, radius and shadows therefore change with
  the theme; for example, Neobrutalism's heavy borders and Terminal's
  monospace type.
- The design is checked in all six presets (Classic, Editorial, Midnight,
  Neobrutalism, Studio, Terminal), light and dark, and with a custom team
  theme.

### 6.5 Playground

`<ApiPlayground>` is a client component themed with `useSiteThemeStyle()`.
It loads on demand (§8.3) into a native `<dialog>`. Escape closes it and
focus returns to the "Try it" button.

**Inputs**
- One input per parameter, grouped by path, query and header.
- Body by content type:
  - `application/json`: raw JSON in a `Textarea`, prefilled from the
    generated example;
  - `multipart/form-data` and `application/x-www-form-urlencoded`: one
    field per top-level property, with a file input for binary properties
    (needed for MediaLit's upload);
  - other types: raw text.
- Server picker with server variables (SendLit self-hosters target their own
  host). Relative server URLs (`/v1`) and a missing `servers` list cannot be
  resolved against the docs site: the import warns, the "Try it" button is
  disabled with an explanation, and code samples use a `{baseUrl}`
  placeholder.

**Auth**
- Inputs follow the operation's requirements (§6.1): nothing for public
  endpoints, a choice when there are alternatives.
- Supported: apiKey in a header or query, HTTP bearer and basic, and
  OAuth2/OIDC by pasting a token.
- Shown as unavailable, with another scheme suggested: cookie apiKeys
  (browsers can't set them) and scheme types the playground doesn't support.
  MediaLit's `signatureAuth` is a plain header apiKey (`x-medialit-signature`),
  so it works like any other API key.

**State**
- Credentials and the chosen server live in one in-memory store per tab,
  shared across operation pages. They survive client-side navigation, not a
  reload, and are never written to storage or sent to FrontLit.
- Secret inputs use `type="password"` and `autocomplete="off"`.

**Requests**
- `fetch` with `credentials: "omit"`, so the reader's own cookies for that
  API are never sent.
- Requests are only sent by clicking "Send"; nothing is sent automatically,
  including from URL parameters.
- Errors are explained:
  - an `http://` server from an `https://` docs page is blocked as mixed
    content;
  - a network `TypeError` is most likely CORS: the message says the API
    must allow the docs origin and the request's headers (such as a custom
    API-key header).

**Response view**
- Status, the headers the API exposes through CORS, and the body as text.
- Non-text responses show only content type and size.

The team's own injected scripts (`codeInjectionHead/Body`) run on the same
page and can read playground inputs. The docs for teams say so.

### 6.6 Admin (`apps/web`)

- The GitHub connection dialog has an "API reference" section: the two
  fields from §4 with a preview (endpoints, URL paths, problems) before
  publishing, then the spec path, URL path, live commit, operation count,
  the latest failed import with its diagnostics, and "Change" / "Turn off".
- Operations do not appear in the docs list, so it isn't flooded with
  generated pages.

## 7. Security summary

| Risk | Mitigation |
| --- | --- |
| Malicious content in the spec (XSS) | Descriptions only through `TextRenderer` or escaped text; spec URLs limited to `https:`, `http:`, `mailto:` (§6.1). No raw HTML. |
| Server-side fetching (SSRF) | The server reads only the spec file from the Git tree and never fetches URLs; no proxy in v1. |
| Parser abuse (YAML bombs, huge specs) | Limits in §4.1. |
| Accidental disclosure of internal endpoints | Preflight and admin state that everything becomes public; `x-internal` / `x-excluded` hide operations (§4). |
| Reader credentials | Memory only, never sent to FrontLit, `credentials: "omit"`, no auto-send (§6.5). |

## 8. Performance

Operation pages are public docs pages, so docs-wide performance applies to
them: caching docs pages and invalidating them on publish (#72), page weight
(#71), and per-page reads, cache warming after publish, link prefetching and
measurement (#140), tracked in #141. This section covers only what is
specific to OpenAPI. The goal: the reference is readable from the first HTML
response, and the playground costs nothing until it is used.

### 8.1 No OpenAPI work at request time

- All parsing, validation, slicing, example and code-sample generation
  happens once, at import (§6.1). Rendering an operation page reads one
  operation row and maps it to primitives.
- Navigation reads only titles and routes. Slices are never part of the docs
  snapshot.
- `apps/sites` never depends on the import code (parser, validation,
  example and code-sample generators). The browser never downloads it.

### 8.2 Server-rendered reference with no JavaScript

- The full reference (method, path, parameters, schema tree, responses,
  examples, code samples) is server-rendered HTML.
- Interactivity uses native elements where possible: `<details>` for schema
  expansion, response sections and sidebar tag groups. The hydrated parts
  are `Tabs` and the sidebar's tag groups, which fetch the other groups'
  operations on first use.
- Bounded HTML size:
  - the schema tree expands two levels by default, and deeper levels are
    collapsed `<details>`;
  - cycles render as a link to the first occurrence instead of recursing;
  - enums longer than about 20 values are truncated with a count.

### 8.3 Playground loads on intent

- The page server-renders only the "Try it" button. The playground's code is
  a separate chunk loaded with a dynamic `import()`:
  - prefetched when the browser is idle or the button is hovered or focused;
  - mounted on click, with focus moved into the dialog.

  This is the same pattern as the chat widget (`site-delivery.md` §6.2).
- The dialog opens on a user action, so it causes no layout shift that
  counts toward CLS.
- Props are a compact playground model precomputed at import: parameters,
  body fields, servers, auth requirements and an example body string. The
  full slice is never serialized into the RSC payload.
- The playground uses `Input`, `Textarea`, `NativeSelect`, `Button` and
  `CodeSnippet`, a native `<dialog>`, and the request builder. No Radix
  components, code editor, JSON-tree viewer or schema-form library.
- Budget: **under 15 KB gzipped** for the playground chunk, and **under 2 KB**
  of extra JavaScript on an operation page before interaction (Tabs).
  Measured by hand in step 4 of the delivery plan.

### 8.4 `/openapi.json`

- Cached under `docs:<team>` and invalidated by the spec activation event.
- `ETag` equal to the spec's content hash, with `304` for a matching
  `If-None-Match`.

## 9. Departures from the issue's expanded design

- **Not tied to the docs release.** The issue proposed an `api_specs` row
  referenced by the release; the API reference has its own live pointer
  instead (decision 2).
- **Single-file OpenAPI 3.x only.** No 2.0 conversion and no `$ref`s to other
  files in v1.
- **Diagnostics in preflight and the admin panel only**, not yet in GitHub
  check runs.
- **No proxy in v1.** The body is raw JSON or simple form fields, not a
  schema-driven form.

## 10. Delivery plan

1. Import (§6.1) with the three fixture specs and the limits.
2. Sync step, tables, activation, diagnostics (preflight, admin panel),
   public endpoints and `/openapi.json`. Operation pages appear with a basic
   render.
3. New primitives, the full reference render, the landing page, the sidebar
   merge, search, chat and sitemap.
4. The playground, loaded on intent, with its size measured against the
   budget.

All four steps are done and were smoke-tested end to end in the browser
against a team connected to a test docs repository, in all six preset
themes (light and dark).

**Later:**
- Semantic embeddings for operations (a background job and a vector table).
- Multi-file specs (`$ref`s to other files) and OpenAPI 2.0.
- Spec diagnostics in the PR and publication check runs.
- Validating docs links to operation pages.
- Method badges in search results.
- `.md` and `llms.txt` exports.
- Playground: proxy (allowlisted to the spec's server hosts, https only,
  private IPs blocked, rate-limited, no body or credential logging),
  schema-driven body form, abort button, binary and large-response handling.
- Multiple specs or versions, 3.1 `webhooks` and callbacks.
- Syntax highlighting.

## 11. Dependencies outside this repo

- The MediaLit API must allow the FrontLit docs origin through CORS,
  including its `x-medialit-apikey` header, before "Try it" can work against
  it. The same applies to SendLit.
- SendLit and FrontLit need a CI step that commits their generated spec.

## 12. Acceptance criteria

- MediaLit's committed `apps/api/src/swagger_output.json` imports from where
  it lives, and the SendLit and FrontLit specs import once committed by CI.
  Each operation has a page under `/docs/<mount>/...`, and `/docs/<mount>`
  shows the landing page.
- An invalid or missing spec leaves the live API reference unchanged,
  reports file, line and JSON pointer in preflight and the admin panel, and
  does not block a docs or pages update in the same commit.
- Changing the spec path or URL path in the dialog takes effect without a
  new push.
- Clearing the spec path in the dialog unpublishes the API reference.
- `/openapi.json` returns the committed spec as JSON, without operations
  marked `x-internal` or `x-excluded`, and those operations have no page and
  no search results.
- Operations appear in site search and chatbot answers, with links to the
  right anchor.
- "Try it" works against the MediaLit API from a FrontLit docs domain,
  including a file upload, with an API key that never reaches FrontLit.
- Operation pages, the landing page and the playground follow the active
  theme in all six presets, light and dark, with no hard-coded colours.
- Operation pages meet the targets in `site-delivery.md` §9, and the
  playground chunk stays under 15 KB gzipped.
