# AI-readable documentation and coding-agent workflows (as of 2026-10-10)

Scope: Mintlify, GitBook, ReadMe, Fern, plus Intercom Fin and Zendesk help-center / AI-agent knowledge. Compared with the FrontLit baseline supplied in the assignment (local/staging sign-off 2026-10-03). FrontLit was not researched on the web. Marketing pages are marked as claims. Tool and file names below are quoted from the official page that names them. Where a page describes a capability but does not publish a tool name, no name is invented.

FrontLit baseline used for every comparison:
- Signed-off release: authenticated administrative MCP and REST can read docs and propose drafts under the same validation and publication rules as the UI. Not a public reader MCP.
- Not in that release (later milestone only): public `/docs/:slug.md`, generated `llms.txt`, reader MCP with `search_docs` and `read_page`.
- Customer chatbot and help-desk suggestions answer only from active published docs (changelog optional). A citation must be supported by the cited passage; otherwise clarify or hand off. Drafts are excluded.
- Coding agents edit Markdown in the customer’s GitHub repo or call the admin API. Live docs change only after the publishing branch imports and the full candidate validates. Open PRs do not change the live site or the chatbot.
- Explicit non-goals: generated API reference, MDX components, autonomous doc generation from the codebase, branch-specific chatbot preview.

## Which products publish llms.txt, llms-full.txt, or per-page Markdown, and since when? Is it on by default?

### Takeaway
By October 2026, Mintlify, GitBook, and Fern generate an `llms.txt` index and per-page Markdown without a customer-authored file; ReadMe exposes both behind Discoverability toggles. `llms-full.txt` is automatic on Mintlify and GitBook and was removed by Fern in June 2026. The llmstxt.org spec (v2, dated 2024-09-03 in search metadata) requires only an H1; `llms-full.txt` is a companion convention, not a required section of that spec.

### Cited Findings

**Specification**
- The llmstxt.org page titled “The /llms.txt file, v2” says the file may live at `/llms.txt` or any subpath, the most specific file wins, and the only required section is an H1 project or site name. Optional pieces, in order, are a blockquote summary, zero or more non-heading markdown sections, then H2 “file lists” of `[name](url)` links with optional notes. Search metadata dates that page 2024-09-03. — [llmstxt.org](https://llmstxt.org/)
- A validator README states there is no IETF RFC as of May 2026 and that the tracked source is the Answer.AI proposal at `https://github.com/AnswerDotAI/llms-txt`. That is a third-party reading of the spec, not the spec itself. — [algorithmix-ai/llms-txt-validator](https://github.com/algorithmix-ai/llms-txt-validator)
- A third-party checker describes `/llms-full.txt` as a companion convention that holds expanded content rather than an index. The spec page retrieved here does not itself define `llms-full.txt`. — [airanklab llms.txt checker](https://www.airanklab.com/tools/llms-txt-checker); spec page [llmstxt.org](https://llmstxt.org/)

**Mintlify (automatic)**
- Mintlify “automatically hosts” `llms.txt` at the site root and at `/.well-known/llms.txt`. It is “always up to date and requires zero maintenance.” A custom root `llms.txt` overrides the generated file; deleting the custom file restores generation. — [Mintlify llms.txt](https://www.mintlify.com/docs/ai/llmstxt)
- The same page documents automatic `llms-full.txt` (also `/.well-known/llms-full.txt`). Each page is title, source URL, description, and full Markdown. Content marked `for="agents"` is included and content marked `for="humans"` is excluded, matching Markdown page visibility. — [Mintlify llms.txt](https://www.mintlify.com/docs/ai/llmstxt)
- Generated `llms.txt` shape: H1 title; blockquote description from `docs.json`; optional “Agent Instructions” if `markdown.instructions` is set; nav-ordered page links that include a `.md` extension; OpenAPI and AsyncAPI spec links; an `Optional` section for absolute nav URLs. Descriptions come from frontmatter, first paragraph, truncated at 300 characters. Default language and version only. Hidden pages and `noindex: true` are excluded unless `seo.indexing` is `"all"`. — [Mintlify llms.txt](https://www.mintlify.com/docs/ai/llmstxt)
- Indexes over 100,000 characters are split. The root file becomes a directory of `/_llms/*.txt` indexes (also served as `.md`). The limit does not apply to `llms-full.txt`. — [Mintlify llms.txt](https://www.mintlify.com/docs/ai/llmstxt)
- Every response, including Markdown and 404s, sends `Link` and `X-Llms-Txt`. The documented `Link` rels are `llms-txt`, `llms-full-txt`, `api-catalog` (only if `download-spec` is enabled), `mcp-server-card`, `agent-card`, and `agent-skills`. Authenticated sites also advertise `oauth-protected-resource`. — [Mintlify llms.txt](https://www.mintlify.com/docs/ai/llmstxt)
- Fully authenticated sites require auth for both files. Partially authenticated sites serve both files publicly but list only public pages. — [Mintlify llms.txt](https://www.mintlify.com/docs/ai/llmstxt)
- Per-page Markdown: “All pages send their content as Markdown to AI agents instead of HTML” and “Every page is also available to view as Markdown by appending `.md` to the URL.” The same page says Mintlify hosts `llms.txt` and `skill.md`, and hosts an MCP server. Page updated 2026-10-02 per search metadata. — [Mintlify AI-native documentation](https://www.mintlify.com/docs/ai-native.md)
- A 2026-03-02 snapshot of Mintlify’s llms.txt doc already said both files are automatic. The October 2026 page adds `.well-known` copies, `Link` headers, agent-instruction blocks, split `/_llms` indexes, and `for="agents"` / `for="humans"` filtering in `llms-full.txt`. Earliest public launch before March 2026 was not found in the pages fetched. — [Mintlify llms.txt snapshot 2026-03-02](https://www.mintlify.com/mintlify/docs/ai/llmstxt); current [Mintlify llms.txt](https://www.mintlify.com/docs/ai/llmstxt)

**GitBook (automatic on published sites)**
- Append `.md` to any published page URL for Markdown. Append `/llms.txt` for an index of “every published page with a Markdown version.” Append `/llms-full.txt` for full content in one file. Docs dated 2026-09-30 in search metadata. — [GitBook LLM-ready docs (getting started)](https://gitbook.com/docs/getting-started/llm-ready-docs)
- Hidden pages are included in `llms-full.txt`. Hiding a page “only removes it from the published table of contents.” — [GitBook LLM-ready docs (getting started)](https://gitbook.com/docs/getting-started/llm-ready-docs)
- An earlier GitBook URL for the same topic (search metadata 2026-07-23) already described `.md`, `/llms.txt`, and `/llms-full.txt`. No changelog entry dating the first launch was retrieved. — [GitBook LLM-ready docs](https://gitbook.com/docs/ai-and-search/llm-ready-docs)
- A 2026 changelog note says published sites serve Markdown to ChatGPT Search’s crawler. Another note says the page-options menu was clarified so hidden pages stay indexed by search, search engines, and LLMs unless indexing is turned off. — [GitBook changelog](https://gitbook.com/docs/changelog)

**ReadMe (toggles, not described as unconditional)**
- AI-Ready Docs (page `updatedAt` 2026-09-25) lists three agent file surfaces: “Markdown for Agents” (`Accept: text/markdown`, all plans), “LLMs.txt” (Markdown index at `/llms.txt`, all plans), and an “AI Dropdown” that copies a page as Markdown or opens it in ChatGPT or Claude (all plans). Getting started tells the admin to turn Markdown for Agents on and “confirm LLMs.txt is on.” — [ReadMe AI-Ready Docs](https://docs.readme.com/main/docs/ai-ready-docs)
- Discoverability (page dated 2026-09-15 in search) says every setting has “a sensible default” and that admins “turn them on” to expose more to agents. Named controls: **LLMs.txt**, **Custom LLMs.txt** (repo-root file stops automatic updates), **LLMs.txt: Split by Section** (`/docs/llms.txt` plus a root index), **LLMs.txt: Split by Category**, **Link Headers** (RFC 8288), and **Agent Hint Banner**. — [ReadMe Discoverability](https://docs.readme.com/main/docs/ai-discoverability)
- Changelog “Upgraded LLMs.txt for AI Agents,” 2026-10-07: `llms.txt` now mirrors the sidebar with nested children; a single “Summarize Index” option links the root file to per-section and per-category files; Markdown pages include `agentTools` front matter pointing at `llms.txt`; a missing `.md` URL returns a Markdown 404 that points at `llms.txt`; guessed URLs such as `/docs.md`, `/reference.md`, or `/docs/<category>.md` redirect to the matching `llms.txt`. — [ReadMe changelog 2026-10-07](https://docs.readme.com/main/docs/changelog/upgraded-llms-txt)
- Markdown responses on ReadMe’s own docs include an `agentTools` block with `siteIndex`, `siteSearch` (`/agentSearch?query=`), `projectIndex`, and `projectSearch`. Seen on the fetched AI-Ready Docs and MCP pages. — [ReadMe AI-Ready Docs](https://docs.readme.com/main/docs/ai-ready-docs)
- No ReadMe page retrieved gives the original ship date of `llms.txt` or states that `llms-full.txt` exists. The October 2026 upgrade doc does not mention `llms-full.txt`.

**Fern (automatic `llms.txt`; `llms-full.txt` withdrawn)**
- Changelog 2025-01-14: “Support for /llms.txt.” Both `/llms.txt` and `/llms-full.txt` shipped then, “auto-enabled like /robots.txt and /sitemap.xml.” — [Fern changelog 2025-01-14](https://buildwithfern.com/learn/docs/changelog/2025/1/14)
- Current docs: Fern generates `llms.txt` at every level of the hierarchy (`/llms.txt`, `/docs/llms.txt`, and deeper). It is a one-sentence description plus URL per page, plus OpenAPI and AsyncAPI links when those exist. Descriptions come from frontmatter `description`, else `subtitle`. — [Fern llms.txt](https://buildwithfern.com/learn/docs/ai-features/llms-txt) and the Markdown twin [llms-txt.md](https://buildwithfern.com/learn/docs/ai-features/llms-txt.md)
- The docs source on GitHub states: “Fern doesn't generate `llms-full.txt`.” Reason given: full-site concatenation exceeded context windows, was expensive to serve, and was little used next to `llms.txt` plus per-page Markdown. — [fern-api/docs llms-txt overview.mdx](https://github.com/fern-api/docs/blob/main/fern/products/docs/pages/ai/llms-txt/overview.mdx?plain=1)
- Changelog 2026-06-12: custom `llms-full.txt` and the `llms-full-txt` key in `docs.yml` are deprecated; Fern no longer generates the file. — [Fern changelog 2026-06-12](https://buildwithfern.com/learn/docs/changelog/2026/6/12)
- That deprecation conflicts with an earlier 2026 directive. Changelog 2026-04-09 said every agent-served page prepends a directive that still pointed at `llms-full.txt`. The June 12 entry is the later official position. — [Fern changelog 2026-04-09](https://buildwithfern.com/learn/docs/changelog/2026/4/9)
- Per-page Markdown: append `.md` or `.mdx`, or send `Accept: text/markdown`. “Any URL that renders as HTML returns its Markdown twin,” including API Reference pages that are absent from nav, `sitemap.xml`, and `llms.txt`. The same Markdown is used for single pages and `llms.txt`, and it honors `<llms-only>` and `<llms-ignore>`. A default per-page directive points agents at `.md` URLs and `llms.txt` and can be overridden in `docs.yml`. Page dated 2026-10-02 in search. — [Fern Markdown access](https://buildwithfern.com/learn/docs/ai-features/markdown)
- `<llms-only>` is served on `/llms.txt` and `.md`/`.mdx` and hidden from the rendered page, Copy page, search widget, and Ask Fern. `<llms-ignore>` is the inverse. Query filters: `lang` (includes `python`, `node`, `java`, `ruby`, `go`, `csharp`, `swift`, and as of 2026-09-18 `php`), `excludeSpec`, `excludeChangelog`. Custom file via `agents.llms-txt` in `docs.yml`. The `llms-full-txt` key is deprecated. — [Fern customize LLM output](https://buildwithfern.com/learn/docs/ai-features/customize-llm-output); PHP filter [Fern changelog](https://buildwithfern.com/learn/docs/changelog)
- Fern blog 2025-10-23 (claim plus product description): API endpoint pages in `llms.txt` include the OpenAPI operation and enabled-language samples; Fern serves Markdown instead of HTML when it detects an LLM bot; dashboard analytics split bot vs human traffic. The “90%+” token figure is Fern’s claim. — [Fern blog, 2025-10-23](https://buildwithfern.com/post/llms-txt-improvements)

**Support products**
- No Intercom or Zendesk page retrieved in this pass documents `/llms.txt`, `/llms-full.txt`, or per-page `.md` exports for the help center. That is an absence of evidence in the sources opened, not a proof those URLs do not exist.

### Inferences
- Public `llms.txt` plus a per-page Markdown URL is the default docs-platform surface in October 2026, not an add-on, except at ReadMe where both are explicit toggles an admin must confirm.
- `llms-full.txt` is no longer unanimous. Fern’s June 2026 withdrawal is the clearest vendor statement that a whole-site dump is the wrong default. Mintlify and GitBook still ship it.
- FrontLit’s signed-off release has neither public `.md` routes nor a generated `llms.txt`. Against Mintlify, GitBook, and Fern, that is the main reader-facing gap. It matches ReadMe only in the sense that ReadMe can leave the files off; ReadMe’s own setup guide tells customers to turn them on.
- Mintlify’s `for="agents"` / `for="humans"` split and Fern’s `<llms-only>` / `<llms-ignore>` are audience filters FrontLit’s baseline does not describe. GitBook’s choice to keep hidden pages inside `llms-full.txt` and LLM indexes unless indexing is disabled is the opposite of “hidden means not retrievable.”

### Gaps
- First ship date for Mintlify `llms.txt` / `.md` before the 2026-03-02 docs snapshot.
- First ship date for GitBook `llms.txt`, `llms-full.txt`, and `.md`.
- Whether ReadMe’s “sensible default” is on or off for LLMs.txt and Markdown for Agents, and whether ReadMe has ever served `llms-full.txt`.
- Whether Intercom or Zendesk publish `llms.txt` or Markdown page exports. Not searched under those exact filenames after the citation searches.

## Which products ship a docs MCP server (reader tools vs writer tools)? What can an agent search, read, or edit? Is write access admin-only?

### Takeaway
All four docs vendors ship a reader MCP and a separate authenticated writer or org MCP. Reader servers do not edit docs. Writer servers are account-authenticated (Mintlify OAuth, GitBook OAuth or PAT, ReadMe `rdme_` API key, Fern org account). Mintlify is the only one that publishes a long explicit tool catalog for the writer. GitBook’s published reader server is documented as read-only without a tool-name list. Fern’s reader server is one unnamed RAG tool, gated on Ask Fern.

### Cited Findings

**Mintlify reader: search MCP, plus WebMCP, plus Index MCP**
- Search MCP is hosted at `{site}/mcp`. Mintlify’s own is `https://mintlify.com/docs/mcp`. Public sites expose it to anyone over indexed public pages. Partial and full authentication must be enabled in the dashboard; the authenticated server is `{site}/authed/mcp`. Discovery: `GET /.well-known/mcp` and `/.well-known/mcp.json`, plus `/.well-known/mcp/server-card.json` and `server-cards.json`. — [Mintlify search MCP](https://www.mintlify.com/docs/ai/model-context-protocol)
- Three tools, described in prose rather than as fixed JSON names: **Search** (snippets, titles, links; optional `version` and `language`); **Query docs filesystem** (shell-style reads, including batch reads); **Submit feedback** (page path plus a problem description, recorded as unhelpful feedback). The server also exposes `skill.md` files as MCP resources. Skills with a `groups` field are limited to matching authenticated users; unauthenticated clients only see skills marked `public: true`. — [Mintlify search MCP](https://www.mintlify.com/docs/ai/model-context-protocol)
- Server-card `tools[].name` values are site-specific. The docs say to use the discovery payload rather than hardcoding a name. The example card uses `search_your_docs`. Built-in search and filesystem tools are annotated `readOnlyHint: true`, `destructiveHint: false`, `idempotentHint: true`, `openWorldHint: false`. — [Mintlify search MCP](https://www.mintlify.com/docs/ai/model-context-protocol)
- WebMCP (Pro or Enterprise) registers tools on `navigator.modelContext` with no extra connection. Official names: `search_docs`, `read_page`, `get_site_overview` (returns `llms.txt`), `read_skill`, `navigate_page`. — [Mintlify search MCP](https://www.mintlify.com/docs/ai/model-context-protocol)
- Indexing defaults to pages in `docs.json` navigation. Hidden pages are excluded unless `seo.indexing` is `"all"`. `noindex: true` and `.mintignore` files are excluded. — [Mintlify search MCP](https://www.mintlify.com/docs/ai/model-context-protocol)
- A 2026-03-02 snapshot said the hosted MCP exposed a search tool, only searched public pages, and could not be generated when every page required authentication. The October 2026 doc adds `/authed/mcp`, filesystem and feedback tools, WebMCP, and OAuth client credentials. — [Mintlify MCP snapshot 2026-03-02](https://www.mintlify.com/mintlify/docs/ai/model-context-protocol); current [Mintlify search MCP](https://www.mintlify.com/docs/ai/model-context-protocol)
- Index MCP at `https://index.mintlify.com` is a separate read-only server across “covered product documentation and the technical web,” unauthenticated. Documented tool: `context` (required `query`; optional `product`; `tokenBudget` default 3000, max 6000). Output is Markdown sections with title, source URL, and source content. The agent, not the server, decides how to apply it. Page search-dated 2026-09-14. — [Mintlify Index MCP](https://www.mintlify.com/docs/search-index/mcp)

**Mintlify writer: admin MCP**
- Endpoint `https://mcp.mintlify.com`. Audience is the team, not end users. OAuth session inherits dashboard permissions. “admin-only actions (such as `update_config` on protected settings) require an admin role.” Client and machine-to-machine tokens are rejected for private-page access. — [Mintlify admin MCP](https://www.mintlify.com/docs/ai/mintlify-mcp)
- Content edits stay on a branch until `save`. `checkout` creates `admin-mcp/<slug>-<sha>` from the deploy branch or attaches to a named branch. `mode: "auto"` (default) opens a pull request. If agent review is push-to-main and the deploy branch is unprotected, Mintlify merges immediately (`merged: true`). `mode: "pr"` always leaves a PR open. `mode: "commit"` pushes to an existing PR branch. — [Mintlify admin MCP](https://www.mintlify.com/docs/ai/mintlify-mcp)
- Checking out the deploy branch itself skips the PR. `save` then commits pending changes straight to that branch, like **Publish** in the editor. Branch protection, a locked editor, “Push directly to your deploy branch” off, or a non-OAuth token forces a session branch instead. — [Mintlify admin MCP](https://www.mintlify.com/docs/ai/mintlify-mcp)
- Content tools named in the doc: `read`, `search`, `edit_page`, `write_page`, `upload_image`, `finalize_image_upload`. Navigation: `list_nodes`, `create_node`, `update_node`, `move_node`, `delete_node`. Config: `update_config` (`docs.json`). Session: `list_deployments`, `checkout`, `list_branches`, `get_session_state`, `diff`, `save`, `discard_session`. — [Mintlify admin MCP](https://www.mintlify.com/docs/ai/mintlify-mcp)
- Project-management tools do not require `checkout` and “apply immediately to the live project” with no branch or PR: `get_deployment_settings`, `get_analytics_report`, `get_workflows`, `list_repos_and_prs`, `update_deployment_settings`, `manage_custom_domain`, `manage_git_source`, `manage_access_auth`, `manage_workflow`, `manage_members_sharing`. The doc’s warning says to confirm before prompting an agent to change workflows, settings, domains, authentication, or members. — [Mintlify admin MCP](https://www.mintlify.com/docs/ai/mintlify-mcp)
- MCP client credentials are not Mintlify API keys. API keys cannot call the MCP server. — [Mintlify search MCP](https://www.mintlify.com/docs/ai/model-context-protocol)

**GitBook reader vs writer**
- Every published site includes a reader MCP if **Page actions** are enabled. Public, share-link-with-all-content-exposed, or fully authenticated sites use `{docs-site-url}/~gitbook/mcp`. Partially authenticated sites use `{docs-site-url}/~gitbook/mcp/auth`. Example: `https://gitbook.com/docs/~gitbook/mcp`. Browser GETs error. HTTP only; `stdio` and `SSE` are not supported. — [GitBook MCP servers for published docs](https://gitbook.com/docs/ai-for-your-readers/mcp-servers-for-published-docs)
- The published server “gives read-only access to your published docs.” It “serves the latest published version only. Drafts and unpublished changes stay private.” It “never exposes account data, analytics, or internal GitBook data.” Hidden pages remain available; hiding only removes them from the TOC. — [GitBook MCP servers for published docs](https://gitbook.com/docs/ai-for-your-readers/mcp-servers-for-published-docs)
- Turning off **Site customization → Page actions** makes `~gitbook/mcp` return 404. **Connect with MCP server** only controls whether the menu shows the URL. — [GitBook MCP servers for published docs](https://gitbook.com/docs/ai-for-your-readers/mcp-servers-for-published-docs)
- Fully authenticated sites use MCP OAuth and Dynamic Client Registration. Supported backends named: Auth0, Azure AD, Okta, AWS Cognito, OIDC, and a custom backend with a Fallback URL. Static visitor auth tokens in headers are not supported. Share-link-only sites are not supported for MCP auth. — [GitBook MCP servers for published docs](https://gitbook.com/docs/ai-for-your-readers/mcp-servers-for-published-docs)
- The published-docs page does not list tool names. It tells the user to ask the client to “List the tools exposed by the my-docs MCP server.” A GitBook blog (search-dated 2026-10-06) claims the published server “lets AI tools search and read the latest published version” and that “draft content stays private.” Treat the verbs “search and read” as that post’s claim; they are not a tool schema. — [GitBook published MCP](https://gitbook.com/docs/ai-for-your-readers/mcp-servers-for-published-docs); [GitBook blog](https://www.gitbook.com/blog/create-documentation-with-ai-and-mcp)
- Writer server: `https://mcp.gitbook.com/mcp`. Docs say Claude Code, Codex, Cursor, and other clients can “create and configure sites, open change requests, draft content, edit pages, and restructure docs.” Auth is OAuth or a personal access token (`Authorization: Bearer`). Streamable HTTP only. Official plugins exist for Claude, ChatGPT, and Cursor. No tool-name inventory is published on that page. — [GitBook MCP](https://gitbook.com/docs/docs-as-code/gitbook-mcp)
- GitBook’s own distinction: published MCP is for readers; GitBook MCP is for “your team’s agents to edit and manage your documentation.” The recommended prompt says “draft new content for my docs in a change request — don’t edit anything live” and ends by sharing the change-request preview link. A different prompt says “Create the site, add the content, and publish.” — [GitBook MCP](https://gitbook.com/docs/docs-as-code/gitbook-mcp)
- GitBook also documents an HTTP ask channel on Markdown URLs, separate from MCP: `GET {page}.md?ask=<question>&goal=<user_goal>` returns “a direct answer to the question and relevant excerpts and sources.” That text is appended to fetched GitBook doc pages as agent instructions. — [GitBook published MCP page](https://gitbook.com/docs/ai-for-your-readers/mcp-servers-for-published-docs.md)

**ReadMe: per-project reader MCP vs ReadMe’s own writer MCP**
- Customer reader server is off until **AI → MCP → MCP Server** is toggled on. URL `https://your-project.readme.io/mcp` (custom domain: `https://your-custom-domain.com/mcp`). Enterprise can merge projects at `https://your-enterprise.readme.io/mcp` and filter with `?projects=slug`. Page `updatedAt` 2026-10-01. — [ReadMe MCP](https://docs.readme.com/main/docs/mcp)
- OpenAPI tools on all plans, names: `list-endpoints`, `get-endpoint`, `search-specs`, `execute-request`, `list-specs`, `get-server-variables`. Documentation tools require the “AI Booster Pack” on this page (the AI-Ready Docs page says “AI Add-on”): `search` (full-text across guides and non-endpoint reference) and `fetch` (full content by ID). Utility tool: `send-feedback`. — [ReadMe MCP](https://docs.readme.com/main/docs/mcp); naming conflict [ReadMe AI-Ready Docs](https://docs.readme.com/main/docs/ai-ready-docs)
- `execute-request` forwards headers from the MCP client config to the customer’s API. Public projects need no ReadMe auth. Private projects need `x-readme-auth` (site password, or `Bearer rdme_…` for teammates-only and custom login). Clients that cannot send headers use `?token=`, which the docs say to treat as a password. — [ReadMe MCP](https://docs.readme.com/main/docs/mcp)
- Query params: `branch` (doc search tools “are not available on branches”), `projects`, `token`, `server` (zero-based server index), `server_variables`. Admins can disable individual endpoints under **Enabled MCP Routes** and can add **Custom Tools** (title, description, instruction body; titles cannot collide with built-ins). — [ReadMe MCP](https://docs.readme.com/main/docs/mcp)
- FAQ: the server “exposes the same content to all users.” Per-user data scoping is only whatever the customer’s own API auth does inside `execute-request`. — [ReadMe MCP](https://docs.readme.com/main/docs/mcp)
- ReadMe’s own writer server, for editing a ReadMe project rather than for the project’s end users, is `https://docs.readme.com/mcp`. Without an API key, read-only access to public docs. With `Authorization: Bearer rdme_…`, “full read/write access to your project.” Page `updatedAt` 2026-09-18. — [ReadMe’s MCP Server](https://docs.readme.com/main/docs/readme-mcp)
- Writer tool names: `search`, `fetch`, `update-docs`, `list-specs`, `search-endpoints`, `list-endpoints`, `get-endpoint`, `execute-request`, `draft-changelog`. The doc says to prefer discovery (`search`, `list-specs`, `search-endpoints`), then inspection (`fetch`, `get-endpoint`), and only then `execute-request` or `update-docs`. — [ReadMe’s MCP Server](https://docs.readme.com/main/docs/readme-mcp)

**Fern: reader RAG server vs private org server**
- Reader server exists “for every documentation site with Ask Fern enabled,” at `your-documentation-site.com/_mcp/server` (example `https://buildwithfern.com/learn/_mcp/server`). “The server exposes a single tool” that answers via the same RAG pipeline as Ask Fern. The page does not name that tool. Queries are semantic; the tool “synthesizes an answer, not a list of raw results.” Each message consumes 2 AI credits. Page search-dated 2026-10-08. — [Fern MCP server for your site](https://buildwithfern.com/learn/docs/ai-features/mcp-server)

## How do Mintlify, GitBook, and ReadMe handle “agent edits the repo, preview deploy, human merges”? Is there a first-class agent/PR flow or just ordinary Git?

### Takeaway
All three have a first-class agent flow that lands on a branch or change request and expects a human merge, and all three also support ordinary Git. None of them make an open PR the live site. Mintlify can be configured to skip the PR and publish, and its non-content admin tools write live immediately. GitBook Agent opens change requests inside GitBook; Git Sync is a separate bidirectional GitHub/GitLab path. ReadMe’s writer MCP creates a branch and a review link, and bi-directional Git sync can override API writes.

### Cited Findings

**Mintlify**
- Admin MCP content path is the first-class flow: `checkout` → edit tools → `diff` / dashboard `editorUrl` → `save`. Default `save` opens a PR. The docs tell operators to “review every pull request before merging.” — [Mintlify admin MCP](https://www.mintlify.com/docs/ai/mintlify-mcp)
- The same `save` auto-merges when push-to-main is on and branch protection does not require a PR. The **Publishing** toggle “Push directly to your deploy branch” is shared with the Slack and dashboard agent (`agentReviewProcess`). Mintlify-hosted sites always push directly unless branch protection requires a PR. Checking out the deploy branch publishes on `save` with no PR. — [Mintlify admin MCP](https://www.mintlify.com/docs/ai/mintlify-mcp)
- `save` needs the GitHub, GitLab, or Bitbucket connection to have write access to the deploy branch’s repository. “`save` opens PRs through the same integration used for normal deploys.” — [Mintlify admin MCP](https://www.mintlify.com/docs/ai/mintlify-mcp)
- The assistant “does not index draft branches or preview deployments.” It reindexes published docs immediately on publish. — [Mintlify Assistant](https://www.mintlify.com/docs/assistant)
- Project-management MCP writes bypass the PR. See the previous section. — [Mintlify admin MCP](https://www.mintlify.com/docs/ai/mintlify-mcp)

**GitBook**
- A change request is “a copy of your main content,” analogous to a GitHub pull request or GitLab merge request. Edits, review, then **Merge**, which “applies the changes to your live docs immediately.” Ways to open one include clicking **Edit**, asking GitBook Agent, or the agent creating one when it detects a documentation gap. — [GitBook change requests](https://gitbook.com/docs/collaborate/change-requests)
- The change-requests screen can filter to requests created by GitBook Agent. Reviewers can approve or request changes. GitBook Agent can be asked to review a request. — [GitBook change requests screen](https://gitbook.com/docs/collaborate/change-requests/change-requests-screen)
- GitBook Agent “works mainly through change requests.” The documented basic workflow is: click **Edit**, open **Agent**, describe the change, review, merge. Bulk find-and-replace also goes through **Start change request** and a **Changes** review before merge. — [How to write documentation with AI](https://gitbook.com/docs/guides/editing-and-publishing-documentation/how-to-write-documentation-with-ai); [Bulk updates guide](https://gitbook.com/docs/guides/editing-and-publishing-documentation/find-and-replace-or-make-batch-changes-across-your-gitbook-docs-with-git-sync)
- Git Sync is bidirectional with GitHub or GitLab. The bulk-update FAQ says external agents (ChatGPT, Codex, Claude) should use Git Sync: “Create a branch, commit the changes, open a pull or merge request, and merge after review.” Local agents can be given GitBook’s `skill.md`. — [GitHub & GitLab Sync](https://gitbook.com/docs/docs-as-code/git-sync); [Bulk updates guide](https://gitbook.com/docs/guides/editing-and-publishing-documentation/find-and-replace-or-make-batch-changes-across-your-gitbook-docs-with-git-sync)
- Writer MCP prompts are the same change-request model, not a direct commit to live, except the “create a site … and publish” prompt which does publish. — [GitBook MCP](https://gitbook.com/docs/docs-as-code/gitbook-mcp)
- Published reader MCP and, by the blog’s claim, draft privacy: unpublished changes are not on the reader server. — [GitBook published MCP](https://gitbook.com/docs/ai-for-your-readers/mcp-servers-for-published-docs)
- API: `POST /v1/spaces/{spaceId}/change-requests/{changeRequestId}/content` applies up to 50 ordered operations atomically (`update_page` accepts `document.markdown`). The doc calls this “the primary way to programmatically author content in a change request” before merge. — [GitBook API batch content changes](https://gitbook.com/docs/developers/gitbook-api/api-reference/change-requests/change-request-content/apply-a-batch-of-content-changes-to-a-change-request)
- Blog claim, search-dated 2026-10-06: GitBook Agent is in beta and future updates will “enable proactive documentation generation based on real-world product signals.” The shipped behavior described is prompt-driven edits and reviews inside change requests, not unattended publish. — [Introducing GitBook Agent](https://www.gitbook.com/blog/introducing-docs-agent)

**ReadMe**
- Writer MCP `update-docs` flow, as documented: find the live version’s stable branch, create a new branch such as `3.0_agent-opus-4-6-update`, edit that branch, verify the write, return a review link “so you can preview the changes and merge when ready.” “Your live docs are never modified directly.” — [ReadMe’s MCP Server](https://docs.readme.com/main/docs/readme-mcp)
- If the project is Git-synced, the MCP “will verify that writes persist after updating. In rare cases where the Git source of truth overrides API writes, you’ll be notified to push the change via Git instead.” — [ReadMe’s MCP Server](https://docs.readme.com/main/docs/readme-mcp)
- Bi-directional sync: a Git repository and the hub are “two views of the same content.” A merge to the version’s branch updates the hub (`npx @readme/cli oas:sync` for OpenAPI). Branches created in GitHub show up in ReadMe and branches created in the ReadMe UI show up in GitHub. Docs also describe **Save to Branch** instead of **Save**. — [Sync docs with OpenAPI](https://docs.readme.com/main/docs/sync-docs-with-openapi); [ReadMe May launch blog](https://readme.com/blog/may-launch)
- Branch reader MCP: `?branch=` connects to a version or branch, but “Doc search tools are not available on branches.” — [ReadMe MCP](https://docs.readme.com/main/docs/mcp)
- Ask AI “searches your published documentation.” “Content is re-indexed every 2 hours.” — [ReadMe Ask AI](https://docs.readme.com/main/docs/ask-ai)
- In-editor **Agent** drafts and edits from the AI panel using the current page and OpenAPI spec. It can be pointed at an indexed codebase. The page does not say those edits publish without a save. Pro plans; Starter has a limited complimentary allowance. Page search-dated 2026-09-09. — [ReadMe Agent](https://docs.readme.com/main/docs/aiagent)
- Launch-blog claim (not the full GitHub AI Writer doc, which was not fetched): “When your team pushes code changes, ReadMe’s AI Writer creates a branch with suggested doc updates for you to review and merge.” The May launch post shows a `readme-ai-writer` bot comment with a ReadMe preview link. The product page claims “Every merged pull request updates your docs.” — [ReadMe May launch](https://readme.com/blog/may-launch); [ReadMe AI marketing page](https://readme.com/ai)
- Changelog 2026-10-07: every AI Agent edit suggestion (page rewrites, API Reference updates, Recipe changes) has its own Apply and Revert controls. That is an in-editor review step, not a Git merge. — [ReadMe changelog 2026-10-07](https://docs.readme.com/main/docs/changelog/upgraded-llms-txt)

**Fern, only as a contrast**
- Fern’s org MCP can read “pull request status and preview URLs for connected repositories.” The fetched page does not say the MCP merges docs or that a preview is what Ask Fern serves. — [Fern’s MCP server](https://buildwithfern.com/learn/docs/ai-features/fern-mcp-servers)

### Inferences
- “Agent edits Git, human merges, open PR is not live” is ordinary practice on all three, and it is also productized: Mintlify `save` mode `"pr"`, GitBook change requests, ReadMe `update-docs` branches. FrontLit’s rule that open PRs do not change the live site or the chatbot matches Mintlify’s assistant (no preview indexing), GitBook’s published MCP (published only), and ReadMe’s Ask AI (published docs; branch MCP has no doc search).
- FrontLit is stricter than the defaults. Mintlify’s default `save` can auto-merge, and checking out `main` publishes. GitBook merge is immediate, but a person or the agent still has to merge. ReadMe’s MCP path keeps a review link, yet the marketing line “every merged pull request updates your docs” describes AI Writer drafts that become live on merge, which is still a human merge if someone clicks merge.
- FrontLit’s “full candidate validates before import” is not described by these vendors. They describe preview links and diffs, not a gate that the whole candidate doc set must validate before the publishing branch is accepted.
- Two different agent loops are easy to conflate. External coding agents plus Git (GitBook skill.md + PR, Mintlify repo + admin MCP PR, ReadMe Git sync) match FrontLit’s intended workflow. In-product agents (GitBook Agent, ReadMe Agent, ReadMe AI Writer, Mintlify dashboard/Slack agent) draft docs from prompts or from code PRs. FrontLit’s baseline says it does not autonomously generate docs from the codebase. AI Writer is the closest thing these products have to that non-goal, and it still lands on a review branch in the launch post.

### Gaps
- The official GitHub AI Writer doc at `https://docs.readme.com/main/docs/github-ai-writer` was not fetched, so bot permissions, which repos it watches, and whether it can merge were not verified beyond the May launch post and the marketing page.
- Whether a Mintlify preview deployment is reachable to humans while remaining invisible to the assistant. The assistant page only says previews are not indexed.
- Whether GitBook Git Sync publishes on merge to the configured branch only, or also updates from unmerged PR branches. The sync page says commits on GitHub or GitLab sync; it does not spell out branch filters in the excerpt retrieved.
- Fern preview-URL behavior versus Ask Fern index. Not stated.

## Do AI answers require quotations or page citations, and can they use unpublished or ticket content?

### Takeaway
None of the official assistant docs retrieved require a verbatim quotation that supports the sentence, or a handoff when support is missing. They show source links, expandable source lists, or inline citation numbers. Mintlify’s assistant and ReadMe Ask AI are published-docs indexes. GitBook Assistant and Intercom Fin can be pointed at non-docs and non-public sources, including tickets or internal notes, and will use them when that toggle is on. Zendesk generative search answers from help-center content the user may view, plus optional external connectors, and withholds answers the user is not allowed to see.

### Cited Findings

**Mintlify Assistant**
- The assistant “cites sources and provides navigable links to take users directly to referenced pages.” It searches documentation as Markdown, uses the page the user is on, and can read images that appear on pages it can access. It does not fetch arbitrary image URLs. — [Mintlify Assistant](https://www.mintlify.com/docs/assistant)

- Page-level or inline citations are table stakes for the in-product assistant. Zendesk generative search is permission-scoped, which can include internal segments the end user is allowed to see, and can include connector content that is not the help center.
- Ticket content: Intercom conversation history is not a Fin source. GitBook connections can put Intercom or Zendesk tickets into the Assistant if exposed. Zendesk Copilot’s use of solved tickets is only in the third-party writeup, so it should not be stated as official. Fern will cite whatever URL an admin adds, including a “support tickets” example.
- Drafts: Mintlify and ReadMe document published-only indexes. GitBook documents published-only MCP and does not say change requests feed the Assistant. FrontLit’s “drafts excluded” matches those docs products and is tighter than Fin, which has no draft/published split for snippets (a saved snippet is live for Fin unless toggled off).
- Staleness: ReadMe’s 2-hour Ask AI reindex and Intercom’s weekly external sync are documented lag that FrontLit’s “active published docs” rule does not have an equivalent for in the baseline. Mintlify claims immediate assistant reindex on publish.

### Gaps
- Whether any vendor’s model is instructed to abstain unless a span of the source entails the answer. Not stated in the docs fetched.
- GitBook Assistant behavior on hidden pages versus pages with indexing off, beyond the changelog sentence.
- Zendesk quick-answers article body, and whether advanced AI agent replies show article links by default. User comments from 2025 discuss missing hyperlinks and a `{{firstDataSourceUrl}}` placeholder; those comments were not re-verified as current product behavior.
- ReadMe Ask AI behavior on unpublished branch content beyond “published documentation” and the branch MCP limitation.
- Fern Ask Fern behavior on preview deployments and on `<llms-only>` content (documented as hidden from Ask Fern, which is the inverse of agent Markdown).

## What “docs for agents” capabilities became table stakes in 2025–2026, and which are still differentiators?

### Takeaway
Table stakes for a developer-docs site in this set are a generated `llms.txt`, a per-page Markdown representation, a reader MCP or equivalent HTTP fetch, source-linked AI answers over the published corpus, and a branch or change-request so agent edits do not go live by themselves. Still differentiating: whole-site `llms-full.txt`, raw page-read MCP versus a single RAG tool, OpenAPI tools that execute live calls, in-browser WebMCP, an admin MCP with a published tool schema, audience-split Markdown, ticket and internal-note grounding, and autonomous drafts from code PRs.

### Cited Findings
- Fern called `/llms.txt` auto-enabled on 2025-01-14 and, in an October 2025 post, quoted a customer calling it “the new standard.” By October 2026 Mintlify and GitBook generate it with no setup, and ReadMe’s own checklist says to confirm it is on. — [Fern 2025-01-14](https://buildwithfern.com/learn/docs/changelog/2025/1/14); [Fern blog](https://buildwithfern.com/post/llms-txt-improvements); [Mintlify llms.txt](https://www.mintlify.com/docs/ai/llmstxt); [GitBook LLM-ready docs](https://gitbook.com/docs/getting-started/llm-ready-docs); [ReadMe AI-Ready Docs](https://docs.readme.com/main/docs/ai-ready-docs)
- Per-page Markdown is documented for all four: Mintlify `.md` plus content negotiation to agents, GitBook `.md`, ReadMe `Accept: text/markdown` when the toggle is on, Fern `.md` / `.mdx` / `Accept: text/markdown`. — [Mintlify AI-native](https://www.mintlify.com/docs/ai-native.md); [GitBook LLM-ready docs](https://gitbook.com/docs/getting-started/llm-ready-docs); [ReadMe AI-Ready Docs](https://docs.readme.com/main/docs/ai-ready-docs); [Fern Markdown](https://buildwithfern.com/learn/docs/ai-features/markdown)
- Reader MCP exists for all four, with different gates: Mintlify automatic for public sites; GitBook automatic if page actions are on; ReadMe toggle; Fern only when Ask Fern is enabled. — [Mintlify search MCP](https://www.mintlify.com/docs/ai/model-context-protocol); [GitBook published MCP](https://gitbook.com/docs/ai-for-your-readers/mcp-servers-for-published-docs); [ReadMe MCP](https://docs.readme.com/main/docs/mcp); [Fern site MCP](https://buildwithfern.com/learn/docs/ai-features/mcp-server)
- Source-linked answers exist for Mintlify, GitBook, ReadMe, Fern, Fin (inline numbers or a private-source disclaimer), and Zendesk (answer derived from the result list the user can open). Citations are not documented as entailment checks. — sources in the previous section.
- Human-gated publish exists as Mintlify PRs, GitBook change requests, and ReadMe review branches. Ordinary GitHub/GitLab sync also exists at GitBook and ReadMe, and Mintlify `save` goes through the project’s Git connection. — [Mintlify admin MCP](https://www.mintlify.com/docs/ai/mintlify-mcp); [GitBook change requests](https://gitbook.com/docs/collaborate/change-requests); [ReadMe writer MCP](https://docs.readme.com/main/docs/readme-mcp); [GitBook Git Sync](https://gitbook.com/docs/docs-as-code/git-sync)
- Differentiators still visible in October 2026 docs:
  - `llms-full.txt` still generated at Mintlify and GitBook; Fern stopped in June 2026. — [Mintlify llms.txt](https://www.mintlify.com/docs/ai/llmstxt); [GitBook LLM-ready docs](https://gitbook.com/docs/getting-started/llm-ready-docs); [Fern 2026-06-12](https://buildwithfern.com/learn/docs/changelog/2026/6/12)
  - Mintlify WebMCP tool names `search_docs`, `read_page`, `get_site_overview`, `read_skill`, `navigate_page` on Pro/Enterprise, with no client install. — [Mintlify search MCP](https://www.mintlify.com/docs/ai/model-context-protocol)
  - Mintlify admin MCP publishes the tool list (`checkout`, `edit_page`, `save`, and the project-management tools that write live). GitBook and Fern describe writer powers without a schema on the pages fetched. — [Mintlify admin MCP](https://www.mintlify.com/docs/ai/mintlify-mcp)
  - ReadMe reader MCP includes `execute-request` against the live API. The others’ reader servers do not document live API execution. — [ReadMe MCP](https://docs.readme.com/main/docs/mcp)
  - Fern’s reader MCP is one synthesized RAG answer, not raw search plus page read, and it is metered at 2 credits per message. Fern also filters `llms.txt` with `lang`, `excludeSpec`, and `excludeChangelog`. — [Fern site MCP](https://buildwithfern.com/learn/docs/ai-features/mcp-server); [Fern customize LLM output](https://buildwithfern.com/learn/docs/ai-features/customize-llm-output)
  - Audience splitting: Mintlify `for="agents"` / `for="humans"`; Fern `<llms-only>` / `<llms-ignore>` with Ask Fern indexing the human text, not the agent-only text. — [Mintlify llms.txt](https://www.mintlify.com/docs/ai/llmstxt); [Fern customize LLM output](https://buildwithfern.com/learn/docs/ai-features/customize-llm-output)
  - GitBook hidden pages remain in `llms-full.txt` and the reader MCP. — [GitBook LLM-ready docs](https://gitbook.com/docs/getting-started/llm-ready-docs); [GitBook published MCP](https://gitbook.com/docs/ai-for-your-readers/mcp-servers-for-published-docs)
  - Support grounding beyond the public docs: Fin internal articles and snippets; GitBook connections including tickets; Zendesk connectors and permission segments; Fern optional extra URLs. — previous section.
  - Agent analytics as a product surface: GitBook **Analyze → Agents & MCP** counts `.md`, `llms.txt`, and MCP separately. Fern dashboard splits AI-provider bot traffic (2025-10-23 post). ReadMe markets MCP metrics. — [GitBook Agents & MCP](https://gitbook.com/docs/analytics/insights/agents-and-mcp); [Fern blog](https://buildwithfern.com/post/llms-txt-improvements); [ReadMe MCP metrics link](https://docs.readme.com/main/docs/mcp-metrics.md)
  - Discovery headers and well-known files: Mintlify `Link` / `X-Llms-Txt` / MCP server card; ReadMe link headers and `/.well-known/mcp/server-card.json` (named “SEP-1649 Server Card” on the Discoverability page); Fern `/.well-known/api-catalog` respects auth as of 2026-06-12. — [Mintlify llms.txt](https://www.mintlify.com/docs/ai/llmstxt); [ReadMe Discoverability](https://docs.readme.com/main/docs/ai-discoverability); [Fern 2026-06-12](https://buildwithfern.com/learn/docs/changelog/2026/6/12)

### Inferences
- Relative to this set, FrontLit’s signed-off release is behind on the reader table stakes (public `llms.txt`, public `.md`, public reader MCP) and aligned on the write table stakes (authenticated admin surface, Git or API edits, no live change until publish, drafts and open PRs kept out of the chatbot).
- The planned FrontLit reader MCP (`search_docs`, `read_page`) would match Mintlify WebMCP’s shape and would be more transparent than Fern’s single RAG tool. It would not, by itself, match ReadMe’s API-execution tools or Mintlify’s admin tool catalog. Those are different jobs.
- FrontLit’s non-goals are real differentiators other vendors sell: Fern and ReadMe treat generated API reference as agent context; Mintlify pages are MDX; GitBook Agent, ReadMe Agent, and ReadMe AI Writer draft docs for humans to merge. Keeping those out is a product boundary, not a missing `llms.txt`.
- The citation rule in FrontLit (passage must support the claim, else clarify or hand off) is not table stakes in these docs. Shipping it would be a differentiator versus source-link UIs. Using unpublished tickets or snippets, which Fin and GitBook connections do, would move FrontLit toward help-desk products and away from its published-only rule.
- `llms-full.txt` should not be treated as mandatory. Fern’s documented reasons (context window, serving cost, low use) are the strongest primary-source argument against it. Mintlify’s 100,000-character split of `llms.txt` is the same pressure on the index file.

### Gaps
- No independent adoption census for 2026. The BuiltWith “>2,000 sites” figure in a 2025-05-28 secondary post is stale relative to this date and was not rechecked. — [getairefs, 2025-05-28](https://getairefs.com/blog/llms-txt-and-llms-full-txt-explained/)
- No head-to-head vendor matrix published by a neutral party in the sources opened. The table-stakes judgment above is an inference from the five vendors’ own docs, not from a survey.

## Any documented failures or limits (hallucinated answers, stale index, MCP auth) from official docs or credible 2025–2026 writeups?

### Takeaway
Official docs mostly document configuration and auth failures, not measured hallucination rates. The concrete limits are: Mintlify `llms.txt` 404 when indexing is disabled, MCP HTTP 429s, and admin writes that skip review; GitBook MCP 404 when page actions are off, plus hidden-page leakage into agent surfaces; ReadMe’s 2-hour Ask AI lag and branch MCP without doc search; Fern JWT expiry with no refresh; Intercom’s weekly external sync and snippet answers that do not link the source; Zendesk’s rephrase fallback when retrieval is thin.

### Cited Findings

**Mintlify**
- If **Don’t index project** is on, `/llms.txt` and `/.well-known/llms.txt` return 404 while `llms-full.txt` still loads. `.md` pages keep linking to `/llms.txt`. Fully authenticated sites 404 or fail both files for anonymous clients, which the help article says is a different symptom. Help article dated 2026-09-24 in search. — [Mintlify help: llms.txt 404](https://www.mintlify.com/docs/help-center/llms-txt-returns-404-but-llms-full-txt-works)
- Search MCP rate limits return HTTP 429: 5,000 requests/hour per IP; 10,000/hour per site for public search and for public filesystem queries; 5,000/hour per site for authenticated search and authenticated filesystem queries. Rolling hour. — [Mintlify search MCP](https://www.mintlify.com/docs/ai/model-context-protocol)
- Authenticated MCP does not accept Mintlify REST API keys. Client credentials are a separate OAuth `client_credentials` exchange at `/authed/mcp/oauth/token`, scope `mcp:search` in the sample response, access token `expires_in` shown as 1209600. — [Mintlify search MCP](https://www.mintlify.com/docs/ai/model-context-protocol)
- OAuth redirect allowlist: Claude, ChatGPT, Cursor, and Devin are always allowed. Other web clients fail auth until their redirect domain is added. Dangerous schemes `javascript:`, `data:`, and `file:` are blocked. — [Mintlify search MCP](https://www.mintlify.com/docs/ai/model-context-protocol)
- Admin MCP: project-management changes apply live with no PR. `save` can auto-merge. Sessions left open leave `admin-mcp/*` branches. Revoking the OAuth grant invalidates the token within 30 seconds but does not close PRs already opened. Private-page tools reject non-OAuth tokens. — [Mintlify admin MCP](https://www.mintlify.com/docs/ai/mintlify-mcp)
- Assistant abstains with “doesn’t have enough information” rather than a documented hallucination rate. It can be stale relative to drafts because it never indexes them; published changes are claimed to index immediately. — [Mintlify Assistant](https://www.mintlify.com/docs/assistant)
- A June 2026 third-party guide says the admin MCP writes nothing live without a PR. That contradicts the current official doc, which allows push-to-deploy-branch and immediate project-setting writes. Prefer the official admin MCP page. — [AIToolsReview, 2026-06-07](https://aitoolsreview.co.uk/insights/mintlify-claude-connector); contradicted by [Mintlify admin MCP](https://www.mintlify.com/docs/ai/mintlify-mcp)

**GitBook**
- MCP URL in a browser returns an error by design. Page actions off returns 404. Clients that need `stdio` or `SSE` cannot connect. Static header visitor tokens cannot authenticate. — [GitBook published MCP](https://gitbook.com/docs/ai-for-your-readers/mcp-servers-for-published-docs)
- Hidden pages are still retrieved by MCP and included in `llms-full.txt`, and a changelog fix says they stay indexed by LLMs unless indexing is turned off. That is a documentation leak if “hidden” was meant as a privacy control. — [GitBook LLM-ready docs](https://gitbook.com/docs/getting-started/llm-ready-docs); [GitBook published MCP](https://gitbook.com/docs/ai-for-your-readers/mcp-servers-for-published-docs); [GitBook changelog](https://gitbook.com/docs/changelog)
- Changelog fix: “large, unpublished spaces” failed to index, so updated pages were not searchable. The tense is a fix note, not a statement that the bug remains. — [GitBook changelog](https://gitbook.com/docs/changelog)
- Writer MCP FAQ documents auth that appears stuck: some clients only start OAuth when tools are listed; browser sign-in can lag; a cached failed server has to be removed and re-added. — [GitBook MCP](https://gitbook.com/docs/docs-as-code/gitbook-mcp)
- Assistant custom instructions cannot override guardrails. No hallucination-rate number. Connections only affect answers after **Expose in search / assistant**. — [GitBook AI Assistant](https://gitbook.com/docs/ai-for-your-readers/gitbook-ai-assistant)

**ReadMe**
- Ask AI reindex interval is 2 hours, so a publish can be invisible to the assistant until the next cycle. — [ReadMe Ask AI](https://docs.readme.com/main/docs/ask-ai)
- `?branch=` MCP connections do not expose doc search tools, so an agent on a preview branch cannot use `search`/`fetch` against that branch. — [ReadMe MCP](https://docs.readme.com/main/docs/mcp)
- `?token=` on a private MCP URL is equivalent to handing out the site password. The server cannot scope docs per end user. — [ReadMe MCP](https://docs.readme.com/main/docs/mcp)
- Git sync can overwrite an MCP `update-docs` write; the server tells the agent to push via Git instead. — [ReadMe’s MCP Server](https://docs.readme.com/main/docs/readme-mcp)
- AI-Ready Docs states ReadMe cannot force a model provider to request `llms.txt` or Markdown. — [ReadMe AI-Ready Docs](https://docs.readme.com/main/docs/ai-ready-docs)
- No official hallucination rate retrieved.

**Fern**
- `llms-full.txt` removal is an explicit limit, not an outage: whole-site files were too large and lightly used. — [Fern changelog 2026-06-12](https://buildwithfern.com/learn/docs/changelog/2026/6/12)
- Reader MCP is absent unless Ask Fern is enabled, costs 2 credits per message, and on authenticated sites returns only public content without `FERN_TOKEN`. Expired JWTs are not refreshed. Header `x-fern-skip-save-query: true` skips analytics but still spends credits. — [Fern site MCP](https://buildwithfern.com/learn/docs/ai-features/mcp-server)
- Ask Fern resolution rate is an LLM judging whether a cited answer was produced, not a human accuracy audit. Queries are retained indefinitely unless a 1–3650 day retention window is set. — [Ask Fern overview](https://buildwithfern.com/learn/docs/ai-features/ask-fern/overview)
- Enabling Ask Fern reindexes, “typically a few minutes,” longer if there are many custom components. Until that finishes, the panel is not up. — [Ask Fern overview](https://buildwithfern.com/learn/docs/ai-features/ask-fern/overview)
- June 2026: unauthenticated `/.well-known/api-catalog` is empty when the site has auth; RBAC-hidden API references are omitted. Before that, catalog leakage is implied by the fix note but not quantified. — [Fern changelog 2026-06-12](https://buildwithfern.com/learn/docs/changelog/2026/6/12)

**Intercom Fin**
- External URL sources “only updated weekly,” against native content that is “almost instantly” ingested. - Official: no generated answer when the query is one or two words or when nothing matches; the UI says to rephrase. ### Inferences
- The failure mode FrontLit already designs for — drafts and open PRs leaking into the chatbot — is one these vendors document and mostly prevent for the public assistant. The failure mode they document less well is confident answers with weak citations. FrontLit’s passage-support rule is a response to a gap the vendor docs do not close with numbers.
- Auth footguns that a FrontLit reader MCP would inherit if it copied 2026 practice: static tokens in query strings (ReadMe), JWTs with no refresh (Fern), OAuth redirect allowlists (Mintlify), and “hidden” content that is still agent-visible (GitBook). FrontLit’s admin-only MCP avoids the public-auth set until the reader milestone.
- Immediate project-setting writes on Mintlify’s admin MCP are the sharpest contrast with FrontLit’s “same publication rules as the UI.” A FrontLit admin MCP that let an agent change auth or membership without the UI’s validation would be moving toward Mintlify’s warning box, not toward the signed-off rule.

### Gaps
- No vendor page retrieved publishes a hallucination or citation-accuracy percentage for 2025 or 2026.
- Mintlify, GitBook, and ReadMe incident reports or status pages for stale search indexes were not searched beyond the docs and changelogs above.
- Zendesk comment threads were not re-tested against the product on 2026-10-10. The official article body is current as fetched; the comments may be fixed or obsolete.
- GitHub AI Writer failure modes (wrong page updated, preview not matching the merge) were not in the sources opened.
