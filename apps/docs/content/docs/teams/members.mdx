---
title: Team members and permissions
description: Invite teammates and give each person only the access they need.
---

Each FrontLit team has one **Owner** and any number of members. The owner can
use every team permission. Every other member receives an explicit set of
permissions; FrontLit does not use stored roles such as Admin or Editor.

The same person can have different access in different teams.

## Invite a teammate

1. Select the team in the workspace switcher.
2. Open **Settings → Members**.
3. Choose **Invite**, enter the person's email address, then choose a preset or
   a custom permission set.
4. Send the invitation. The recipient must sign in with that same email
   address before they can review and accept it.

Invitations expire after seven days. You can resend or revoke a pending
invitation from the Members screen. Resending creates a new link and makes the
previous one unusable.

## Choose permissions

Presets are shortcuts, not roles. Choosing one copies its permissions into the
member's access; you can then use **Custom** when a different combination is
needed.

| Preset          | Intended access                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------- |
| Full access     | All non-owner team permissions. It does not grant ownership or API-key management.                                  |
| Content manager | Pages, themes, media, blog, help docs, and changelog content.                                                       |
| Support         | Inbox/help desk and help docs.                                                                                      |
| Marketing       | Contacts, segments, and broadcast drafting. Sending a broadcast requires the separate `broadcasts:send` permission. |
| Read only       | Read access across available product areas.                                                                         |
| Custom          | Select the exact permissions to grant.                                                                              |

Write permissions include the matching read permission. For example,
`pages:write` also lets a member view pages. Some permissions are marked as
sensitive in the picker because they can affect members, domains, AI settings,
general settings, or live broadcasts.

## What members see

FrontLit hides workspace areas a member cannot access. If someone follows an
old bookmark or switches to a team where their current page is unavailable,
FrontLit takes them to the first area they can access instead. This keeps the
workspace focused, but permissions are always enforced by the API as well.

A member may be able to view a screen without having permission to change it.
Controls they cannot use are disabled or omitted. If permissions change, the
next request uses the new access immediately.

## Manage members safely

Members with **Members: invite** can invite people only with permissions they
already hold. Members with **Members: manage** can edit or remove only
non-owners whose access is no broader than their own. This prevents someone
from granting or changing authority above their level.

The owner can edit or remove any non-owner. A member can leave a team at any
time. The owner must transfer ownership to an existing member before leaving
or deleting the team. Ownership transfer and team deletion require a fresh
email-code verification.

## Owners and API keys

The team owner is identified by the team itself, not by a permission preset.
Owners cannot be edited or removed through the member editor. Transfer
ownership when responsibility changes.

Team API keys currently have full-team access, so only the owner can create,
list, or revoke them. Treat every API key as a sensitive integration secret.

## OAuth scopes are separate

Human permissions control what a signed-in person may do in a team. OAuth
scopes control what an external client may do for that person. For an OAuth
request to succeed, **both** the current team permission and the token's scope
must allow the action. Changing team permissions takes effect immediately,
even for a token that still has a matching scope.

See [Authentication](/developers/authentication) for API keys, browser team
selection, and OAuth authentication details.
